### **Feature Overview**

This bug fix addresses a thundering-herd problem in fullsend's CSMA/CD-style GitHub API rate-limit handling. When multiple runners hit a 429 or secondary rate limit, `_github_csma_sleep_after_rate_limit` sleeps until the reset timestamp but all runners wake simultaneously, re-triggering rate limits. The fix extracts the post-reset spread logic (already present in `github_csma_sense`) into a shared helper `_github_csma_post_reset_spread` and calls it from both sleep-until-reset paths, adding a random delay (0 to `GITHUB_CSMA_SPREAD_MAX_SEC`, default 60s) to desynchronize runners.

#### **2. Known Limitations**

- The spread uses `$RANDOM` (bash built-in, 0–32767), which provides only 15 bits of entropy. For large runner fleets (100+), collisions in spread delay are possible but unlikely given the default 60-second range.
- The spread is integer-second granularity only; sub-second jitter is not supported.
- No observability/metrics are emitted for the spread delay — it is logged to stderr only.

### **II. Software Test Plan (STP)**

This STP serves as the **overall roadmap for testing**, detailing the scope, approach, resources, and schedule.

#### **1. Scope of Testing**

Testing covers the addition of post-reset spread to `_github_csma_sleep_after_rate_limit` in `internal/scaffold/fullsend-repo/scripts/lib/github-api-csma.sh`. The scope includes the new `_github_csma_post_reset_spread` shared helper function, its integration into both rate-limit sleep paths, configuration via `GITHUB_CSMA_SPREAD_MAX_SEC`, and regression verification of existing CSMA retry behavior.

**Testing Goals**

- **P0:** Verify that `_github_csma_sleep_after_rate_limit` adds a random spread delay after sleeping until the rate-limit reset timestamp
- **P0:** Verify that `GITHUB_CSMA_SPREAD_MAX_SEC=0` disables the spread entirely
- **P0:** Verify existing `post-prioritize-test.sh` tests continue to pass without modification
- **P1:** Verify that the shared helper `_github_csma_post_reset_spread` is called from both `github_csma_sense` and `_github_csma_sleep_after_rate_limit`
- **P1:** Verify concurrent runners wake at staggered times rather than simultaneously
- **P2:** Verify spread range is bounded by `GITHUB_CSMA_SPREAD_MAX_SEC` value

**Out of Scope (Testing Scope Exclusions)**

- [ ] **GitHub API rate-limit enforcement behavior** — Platform-level behavior; fullsend tests its own retry logic, not GitHub's rate-limit implementation.
- [ ] **Exponential backoff algorithm correctness** — Pre-existing `github_csma_backoff` function is unchanged and already tested.
- [ ] **Network-level retry behavior** — Transport-layer retries are outside the CSMA library scope.

#### **2. Test Strategy**

**Functional**

- [ ] **Functional Testing** — Validates that the feature works according to specified requirements and user stories
  - *Details:* Verify spread helper adds delay in range [0, SPREAD_MAX_SEC] after rate-limit sleep. Verify SPREAD_MAX_SEC=0 disables spread. Verify both code paths call the shared helper.
- [ ] **Automation Testing** — Confirms test automation plan is in place for CI and regression coverage (all tests are expected to be automated)
  - *Details:* All tests are shell-based and run in CI via `post-prioritize-test.sh`. New spread tests should follow the same mock-based pattern.
- [ ] **Regression Testing** — Verifies that new changes do not break existing functionality
  - *Details:* Run existing `post-prioritize-test.sh` suite (happy-path, rate-limit-retry, auth-error, exhausted-retries, exit0-rate-limit scenarios) to confirm no regressions.

**Non-Functional**

- [ ] **Performance Testing** — Validates feature performance meets requirements (latency, throughput, resource usage)
  - *Details:* Not directly applicable. The spread intentionally adds delay (up to 60s default) to prevent thundering herd. Verify the delay does not exceed SPREAD_MAX_SEC.
- [ ] **Scale Testing** — Validates feature behavior under increased load and at production-like scale
  - *Details:* Not applicable for unit/functional testing. The desynchronization benefit manifests at scale (5+ concurrent runners) but is validated by design analysis.
- [ ] **Security Testing** — Verifies security requirements, RBAC, authentication, authorization, and vulnerability scanning
  - *Details:* Not applicable. No authentication or authorization changes.
- [ ] **Usability Testing** — Validates user experience and accessibility requirements
  - *Details:* Not applicable. Infrastructure library change with no user-facing interface.
- [ ] **Monitoring** — Does the feature require metrics and/or alerts?
  - *Details:* The spread logs a message to stderr ("Post-reset spread: sleeping Ns..."). No metrics or alerts are required.

**Integration & Compatibility**

- [ ] **Compatibility Testing** — Ensures feature works across supported platforms, versions, and configurations
  - *Details:* The script uses POSIX-compatible bash constructs (`$(( ))`, `$RANDOM`). Should work on all supported runner OS versions.
- [ ] **Upgrade Testing** — Validates upgrade paths from previous versions, data migration, and configuration preservation
  - *Details:* Not applicable. The library is scaffolded fresh on each repo install; no upgrade path for in-place updates.
- [ ] **Dependencies** — Blocked by deliverables from other components/products
  - *Details:* No external dependencies. The fix is self-contained within the CSMA library.
- [ ] **Cross Integrations** — Does the feature affect other features or require testing by other teams?
  - *Details:* All callers of `_github_csma_sleep_after_rate_limit` (`github_csma_run`, `github_csma_run_pipe`, `github_csma_run_cmd`) and `github_csma_sense` now invoke the spread. Scripts sourcing `github-api-csma.sh` (e.g., `post-prioritize.sh`) inherit the behavior automatically.

**Infrastructure**

- [ ] **Cloud Testing** — Does the feature require multi-cloud platform testing?
  - *Details:* Not applicable. Shell library runs identically on all GitHub Actions runner OSes.
